# TASK-021 — Activity-driven cross-device deletion awareness

## Original request / goal

Two inspectors use separate devices: one edits an inspection while the other deletes it. Fetch server changes without polling/network flooding; checks are triggered by mouse, screen or key activity. User explicitly chose a minimum 30-second interval. Preserve offline-first work and the deleted-editor recovery UX.

## Constraints and file scope

Use the existing private shared-owner API, per-tab in-memory credential, sync Web Lock, immutable FIFO payloads and IndexedDB stores. No per-user isolation, WebSocket/SSE service, background read polling, broad rename-conflict protocol, schema rewrite, queue compaction or production test writes. Existing push/reconnect/retry behavior is separate from the read throttle and remains unchanged. PWA update checks are also separate. This task deliberately adds a backward-compatible server migration; no IndexedDB version/store change.

May change focused activity/API/sync modules and hook/App UI, db reconciliation/metadata helpers, server app/new migration, focused existing/new tests/browser fixtures, CI browser gate and relevant README/context/deployment/task registry. Protect applied migration001, credentials/env, existing deployment resources and unrelated features/history. No new dependency needed. Production backend rollout precedes frontend, through existing migration release command; no direct production database testing.

## Acceptance criteria

1. Mouse/touch pointerdown/pointermove, keydown, scroll, focus and return-to-visible may request an activity read. Explicit Connect may request the initial snapshot after existing upload work. No read timer, trailing/debounced scheduled request, startup read without activity, or online-alone read. Eligibility requires visible+online and valid configured/connected API (development loopback works without owner token). Activity bursts are ignored during 30 seconds and during an active request; no backlog of queued checks. A quiet page makes zero activity GETs regardless of elapsed time. Event listeners clean up; no credential/data broadcast.
2. The same sync Web Lock spans rate reservation, GET and committed reconciliation. A durable syncMetadata reservation scoped to API base limits actual GET starts across same-origin tabs/reloads to one per30seconds; failures consume the interval. Future/invalid reservation values fail closed for that attempt and are repaired to now so the next activity after30sec may retry. In-memory attempt throttling avoids DB/lock work per raw event. One in-flight per coordinator, no automatic read retries. Hidden/offline/disconnect/unmount abort; response application rechecks lifetime/credential/base generation and abort inside the local transaction. Stale/unauthorized/failed/malformed/oversized response never clears data.
3. Add authenticated GET /api/inspections/snapshot before the id route. A single SQL statement returns one MVCC snapshot {inspections, deletedIds}; existing row fields retain their contract. Each collection is limited to5000: query5001 and reject the entire response if exceeded, never truncate/apply partially. Client validates full shape, UUID uniqueness, title/status/timestamps and no active/deleted overlap, with bounded response and timeout8sec. This private bounded dataset has no pagination/delta efficiency guarantee; document this limit.
4. Migration002 adds permanent inspection tombstones (UUID PK, deletion timestamp). Authenticated syntactically valid DELETE retires the UUID atomically with deletion, including DELETE404. Retain current204/404 contract; invalid/unauthorized requests cannot retire IDs. POST and DELETE for the same UUID serialize transactionally so replayed CREATE cannot recreate a retired UUID (409 INSPECTION_DELETED); PATCH remains non-upserting404 when missing. No tombstone garbage collection; old offline clients may replay arbitrarily late. Old routes and normalized CREATE replay retain compatibility.
5. Apply validated snapshots in one existing-store transaction: explicit tombstones remove local live records and prevent future local updates, including delayed notification/Save; never infer deletion from absence. Preserve all pending CREATE/UPDATE/DELETE payloads, ordering, metadata sequence and atomic local writes. For active remote records, any local pending operation for that ID prevents overwriting/recreation; otherwise import current remote fields. Existing unknown local-only rows absent from snapshot remain. Tombstoned pending changes stay visibly blocked for explicit review/discard; do not drop queue entries automatically. Verified missing UPDATE or retired CREATE response also marks the local record deleted safely without losing queued payload. General concurrent remote rename/status retains existing last-successful-write semantics, outside this delete/edit task.
6. Reuse stable deleted-editor recovery UI: remote deletion preserves selectable unsaved title/create input, disables Save/mutations and permits explicit dismissal; message says another tab or device. Snapshot work blocks PWA apply while active, without forcing reload. Other tabs reread local data from commit notifications. Show safe read errors separately from upload errors; a read failure does not silently disable offline CRUD or discard mutations.
7. Deterministic tests cover eligible events/bursts/idle/no trailing timers,30sec shared reservation including reload/failure/future-invalid values, one in-flight/abort/stale generations, malformed/empty-vs-failed snapshot, pending/unknown-record merge and atomic rollback, tombstone local guard and unchanged queue. Real PostgreSQL tests prove retire/delete/latePATCH/CREATE replay and concurrent CREATE/DELETE; no resurrection. Actual two independent browser contexts with separate storage and disposable API/PostgreSQL prove initial download, remote delete while editing, text retention/blocked Save, offline queued UPDATE then server deletion, bounded reads on trusted user activity, idle/hidden/disconnected no reads, next activity convergence, and no token persistence. Existing gates/PWA/browser tests stay green.
8. Requirements approval precedes code; implementer self-review, independent exact-head approval and full configured CI precede merge. Record backend then frontend rollout, exact SHA/Pages full workflow and safe hosted verification. Use synthetic disposable data for writes; hosted checks do not manipulate production inspections/tokens. Registry completion uses separate reviewed reconciliation PR after applicable evidence.

## Assumptions / unresolved questions

Origin/profile tabs share reservation; separate devices each have their own30sec budget. A response is authoritative at read time, not a live subscription: later server changes appear on a later eligible user action. Both devices must connect to the same configured API with the owner credential; no new login/accounts. Deletion must reach the server before another device can learn it. Offline/idle devices may remain stale; commit-time server checks remain necessary. No critical requirement remains unresolved after user interval selection and independent design comparison.
